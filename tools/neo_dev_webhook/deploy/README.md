# Receiver and persistent-profile staging

Nothing in this directory deploys automatically. Deployment, service restart, ingress, secrets, and access changes remain separately authorized operations.

`hermes-stage.sh install` records exact present/absent state for every managed path, replaces the receiver Python package, installs the repository-owned fixed-routing helper at `/opt/data/scripts/neo-dev/task.py` and phase reconciler at `/opt/data/scripts/neo-dev/reconcile-phase.py`, removes backed-up obsolete Hermes-scope plugin/marker/adapter/library paths, and replaces the marked block in the existing persistent `dev` profile. It rejects malformed managed-block markers before mutation. It never touches credentials or remote controller state. It does not install a plugin, change toolsets, disable execution tools, create a profile, or install controller software. `verify` requires exactly the three approved package files, exact helper bytes, the profile contract, and absence of obsolete paths. `rollback <backup>` restores the exact prior presence and bytes for only that scope. Fixture operations exercise reversible staging without touching a live profile.

The data root is canonicalized before any managed path is derived. Every spelling or symlink resolving to real `/opt/data` requires `NEO_DEV_DEPLOY_AUTHORIZED=MICHAEL_APPROVED`; every other root must canonically end in `/opt/data` beneath a root carrying `.hermes-scope-fixture`. Arbitrary alternate roots fail before snapshot or mutation. After snapshot, install is transactional across ordinary failures and INT/TERM/HUP: its trap restores the exact scope and is disarmed only after verification succeeds.

The helper strictly accepts `--board private-dev`, `--assignee dev`, and `--workspace dir:/opt/data/profiles/dev`. It holds `/opt/data/.neo-dev-task-create.lock`, resolves the private-dev database through `hermes_cli.kanban_db`, pins that exact path into both CLI calls with `HERMES_KANBAN_DB`, and creates with the repeatable `--skill snapflow-orchestrator` option supported by the pinned host. It reconciles every uncertain result against the same database, emits exactly one compact durable JSON document, and bounds its best-effort dispatcher wakeup. No executable path or routing value is runtime-overridable or derived from webhook input.

The phase reconciler accepts explicit `--repo`, `--issue`, and `--phase` inputs, rejects every repository except `kingkill85/snap-flow`, rejects closed Issues, pull requests, and Issues without `neo-dev`, and invokes `/home/dev/bin/gh` unless an absolute executable is supplied. It adds the expected phase label and removes stale phase labels through label-scoped endpoints without rewriting non-phase labels, then re-fetches and verifies exactly one expected phase label. It emits one compact JSON success result; any mutation or verification failure exits nonzero. Authentication remains entirely with `gh` and no token is accepted, stored, or logged by the helper.

Hermes v0.20.0 provides a deliberately non-unique `idx_tasks_idempotency(idempotency_key)` index and application-level non-archived deduplication. The managed helper adds the required stronger serialization with its global flock and authoritative all-status reconciliation before creation; the verifier pins the observed non-unique index rather than fabricating a uniqueness constraint.

Before any separately authorized staging on the development host, run the pinned read-only compatibility check from the repository checkout:

```bash
python3 tools/neo_dev_webhook/deploy/verify_hermes_contract.py
```

It requires the independently observed `/opt/hermes` installation and exact `Hermes Agent v0.20.0 (2026.8.3)` contract recorded in `hermes-contract.v0.20.0.json`. It compares the complete create/dispatch long-option sets, the complete ordered `PRAGMA table_info(tasks)` result, and the idempotency index shape. It opens the resolved `private-dev` SQLite database in read-only mode and never creates or changes a task. Absence, extra fields/options, or any drift is a failure, not a skipped or fabricated pass.

The cleanup order is intentionally explicit and entirely undeployed: first confirm controller inactivity; then, only with Michael's separate access-change authorization, use `controller-access-retire.sh`; then, only with separate deployment and destructive persistent-state authorization, use `controller-retire.sh`; only afterward may separately authorized receiver/profile staging be considered. `controller-access-retire.sh` rejects any account home other than exactly `/home/neo-controller`, repeats the observable inactivity scan, and SHA-256 seals only that home’s `.ssh` state plus the account's exact shell and password hash in a root-only backup. It removes the SSH directory, locks the account, selects `/usr/sbin/nologin`, verifies the result, and automatically restores those exact fields/state on any mutation or verification failure. Rollback verifies backup integrity and uses `usermod`; it never restores shared passwd/shadow files. It does not touch global sshd configuration, other users, or externally managed credentials.

`controller-retire.sh` is root-only code/state cleanup machinery, not an alternate orchestrator. It requires its own deployment and destructive persistent-state authorization, an explicit inactivity assertion, and a successful observable process scan. It backs up exact present/absent state for only the listed old install paths, seals the archive with SHA-256, and verifies it before rollback. Neither retirement script is run by staging or authorized for execution by this repository change.

Production controller retirement requires `CONTROLLER_RETIRE_AUTHORIZED=MICHAEL_APPROVED`; its sealed snapshot is transactionally restored on partial removal, verification failure, or INT/TERM/HUP, and success is reported only after the absence verification passes.

The single receiver authenticates and filters the webhook, then synchronously invokes the fixed task helper. The helper uses the canonical delivery UUID as its idempotency key and authoritatively creates or reconciles exactly one durable task in the `private-dev` Kanban database. A retry that follows an ambiguous response reaches the same task identity. `dockge-activate.sh` and `verify_live_compose.py` only verify or reversibly recreate that one already-defined receiver service when separately authorized.
