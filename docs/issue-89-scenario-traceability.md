## Manual-test failure gap analysis

At approved revision baseline `fa6cb26c4045ca556f724a5036d27227fd650149`, a production-shaped project could persist `test: 1` and `test2: 2` on a normal 120×90 stored Area and expose both values in Edit Area while both renderers painted nothing. The shared descriptor itself was not divergent: its canonical low-zoom envelope was wider and taller than the stored Area, every prior candidate was constrained inside that Area, and every candidate collided with the Area's own canonical name-label obstacle. The shared layout therefore returned no descriptor to either SVG or canvas. Earlier runtime fixtures created oversized 500×300 Areas, while focused renderer tests called the model with favorable synthetic geometry; those oracles proved parity only after a descriptor existed and never carried a normal stored aggregate through the production adapters.

The revised regression closes that oracle gap by building an existing-project-shaped graph through authenticated Product Type, parameter, project, floorplan, Area, and atomic Area APIs; asserting the stored vertices and values; reopening the actual editor; then carrying the same normally loaded state to direct SVG text nodes and the existing PNG export. It requires recorded fill/background calls, a valid downloaded PNG, and decoded light/dark contrast pixels. The focused geometry test separately preserves a no-safe-placement omission class. Content-sized lower-left canonical candidates now enclose the same per-line Area-name-style treatment in SVG and canvas, so recognizable parameter identity and value remain visible while full Product Type name/stable identity remains accessible and all existing product/name/prior-annotation/image collision checks continue to apply.

The compound-control revision replaces the superseded native-spinner oracle with application-level equivalence classes: one and multiple Product Types; desktop and 390px phone layout; direct entry, both Arrow keys, and both explicit buttons; 0 and 9999 boundaries; temporary blank-as-zero; fractional, negative, non-digit, non-finite, and out-of-range retained drafts; ordinary decrement/value/increment tab order with visible focus; associated labels/bounds/errors; and direct Area-mutation counting. Screenshots and the real browser's computed boxes, rather than class names alone, establish compact alignment and minimum targets.

At blocked implementation `83fc0574a4e20d07622107710ec6fd95fa556e0c`, the API correctly persisted real editor values, but the shared display-line truncator consumed the parameter/value suffix after a long Product Type name. The SVG oracle used descendant text content, so hidden `<title>` content satisfied its assertion even when the direct painted text omitted the value. The PNG oracle required only a Product Type prefix in `fillText`/`strokeText`, so the same incomplete painted line passed there. Earlier persistence scenarios also split UI save/reopen from annotation/export fixtures instead of carrying one real saved aggregate through both consumers.

The corrected evidence treats these as equivalence classes rather than one fixture:

- persisted API values and freshly entered values: backend route coverage plus the real editor scenario's four successful revisions and final aggregate;
- interactive SVG and PNG: direct SVG text-node content, full accessible name, actual shared canvas draw calls, downloaded PNG bytes, and the existing decoded-pixel contrast checks;
- first load, refetch, and version switch: reload coverage in the positive-only scenario, explicit page refetch during repeated saves, and copied-version interactive annotation evidence in the Create Version scenario;
- zero, positive, and multiple Product Types: final `[4, 0, 2, 0]` aggregate with both positive groups painted and both zero rows absent;
- ordinary and low zoom: persisted-value evidence at ordinary zoom plus the existing 25%, fitted-below-25%, 50%, 100%, and 150% painted-boundary matrix;
- narrow and wide viewports: real Chromium input bounding boxes and computed padding/alignment at 390px and 1440px;
- successful, repeated, and failed saves: four sequential real UI saves with monotonic unique revisions, plus existing visible/non-destructive validation, stale-revision, and changed-applicability recovery scenarios. The reported one-off save failure was not reproduced in the bounded repeated/refetch matrix, so no unsupported cause is assigned.
